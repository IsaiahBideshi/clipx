# AGENTS.md

## What this repo is

- **ClipX** = Windows Electron desktop app (React 19 + Vite renderer) + a Vercel deployment (`clipx.bideshi.tech`) that serves the marketing site (`public/landing/`) and serverless API functions (`api/`). Supabase is the database and auth provider.
- The React app in `src/` **only runs inside Electron** — it is never served in a browser. The one exception is `src/sharePlayer.jsx`, which bundles `VideoPlayer` for the public `/clip/<id>` share page (see `build:player`). Packaged builds serve `dist/index.html` from a local HTTP server started in `electron/main.js` (with SPA fallback). Routes use `HashRouter` (`#/`, `#/settings`, `#/library`, `#/profile`, `#/signup`, `#/login`).
- Renderer ↔ main process communication goes through `window.clipx.*` IPC methods exposed in `electron/preload.js`. Anything new in preload must be mirrored in the renderer, and vice versa.
- Main process is ESM (`"type": "module"`) — use `import`/`export` everywhere, including `api/`.

## Commands

PowerShell here has execution-policy disabled, so **`npm` fails; always use `npm.cmd`**.

- `npm.cmd run dev` — starts Vite on `127.0.0.1:5173` then launches Electron (loads the dev server URL). This is the dev loop; Electron must open for most features to work (IPC, keytar, better-sqlite3).
- `npm.cmd run build` — `vite build` then `electron-builder --win`; outputs `dist/ClipX-Setup.exe` + `latest.yml` (used by electron-updater).
- `npm.cmd run build:react` / `build:electron` — the two halves separately.
- `npm.cmd run build:player` — bundles `src/sharePlayer.jsx` into `public/clip-player/` for the `/clip/<id>` share page. Vercel has no build step, so the output is committed: re-run it and commit after changing `VideoPlayer.jsx`, `player.css` or `playerPrefs.js`.
- `npm.cmd test` — runs `tests/**/*.test.js` with Node's built-in test runner (`node:test`, no extra dependencies). Tests live in `tests/`, not next to the source, because electron-builder packages everything under `electron/`. Only import modules that load in plain Node: no `electron` import, no Supabase client created when the module loads (e.g. `api-handlers/auth.js`), and no `import.meta.env` at the top level.
- `eslint.config.js` exists but the eslint packages are **not installed** and there is no lint script — do not claim to run lint.

## Env & secrets

- Secrets live in the gitignored `.env` (Supabase service-role key, Google/Twitch IGDB keys, etc.). Never commit them or echo their values. `.env.local` is not used by the app — if `vercel env pull` creates one locally, it's only for the Vercel CLI (`vercel dev`).
- `electron/main.js` loads `.env` via `dotenv/config`; the renderer gets `VITE_*` from the same `.env` at build time. No service loads `.env.local`, so nothing can clobber `process.env`.
- Renderer-side API base: `import.meta.env.VITE_DATABASE_URL`, defaulting to `https://clipx.bideshi.tech` (see `src/lib/accountApi.js`).
- Google OAuth client ID/secret are fetched at runtime by the main process from `{API_BASE}/api/keys`, not read from env directly.
- IGDB game search/lookup goes through `{API_BASE}/api/games` (signed-in users only). The server reads `IGDB_CLIENT_ID` + `IGDB_CLIENT_SECRET` from its env, so the Electron app needs no IGDB keys. `api-handlers/igdb.js` gets a Twitch app token from those, keeps it in memory, and gets a new one when IGDB answers 401, so nothing needs renewing by hand. If game search breaks with Twitch token errors, check the secret in Vercel.
- Auth in the renderer uses Supabase with a custom storage adapter that persists sessions via IPC (`window.clipx.authStorage*`), falling back to `localStorage` outside Electron.

## Gotchas

- `better-sqlite3` and `keytar` are native modules and break under Electron's ABI after a fresh `npm install`. The error message in `electron/services/clipIndexService.js` tells users to run `npm.cmd run rebuild:electron`, but **that script does not exist** in `package.json`. `@electron/rebuild` is present transitively (via electron-builder); use `npm.cmd exec electron-rebuild -f -w better-sqlite3 -w keytar` (or add the missing script).
- Clip metadata lives in SQLite at `%APPDATA%/clipx/clip-index.sqlite` (WAL mode, chokidar-watched folders), plus a legacy `clipsData.json` in `%APPDATA%/`. In dev, userData is redirected to `%APPDATA%/clipx-dev`.
- FFmpeg: `ffmpeg-static` + fluent-ffmpeg; ffmpeg binary must stay unpacked (`asarUnpack`), handled by `electron/utils/ffmpeg.js` (`app.asar.unpacked` path rewrite).
- Google OAuth uses a PKCE loopback flow on an OS-assigned `127.0.0.1` port (a fixed port can land in a Windows excluded port range and fail with `EACCES`). The app sends its `redirect_uri` to `/api/google/token`, which falls back to port **51723** for builds up to v1.2.5 that don't send one. YouTube refresh tokens are stored in the OS keychain via keytar.
- Uploads above ~10 Mbps also get a 1080p, ~8 Mbps stream copy stored next to the original as `<blob_name without .mp4>.stream.mp4` in the `clips` container. There is no DB column for it: the name is derived in both `electron/utils/streamCopy.js` and `api-handlers/clips/azure.js`, so change them together. `/api/clips/stream` and `/clip/<id>/video` serve the copy when it exists and fall back to the original; `scripts/backfill-stream-copies.js` creates copies for clips uploaded before this existed.
- In-app clipping (`electron/services/obsService.js`, settings on the `#/recording` page) drives portable OBS that ClipX downloads into `userData/obs/<version>`. The version is pinned by `OBS_VERSION` + `OBS_ZIP_SHA256` in `electron/utils/obsConfig.js`; bump both to upgrade, and check the new version for startup dialogs (first-run wizard, What's New, safe mode) first, because ClipX rewrites OBS's config on every launch. OBS runs in Advanced output mode, with the encoder's CBR bitrate in the profile's `recordEncoder.json`: Simple mode has no bitrate setting for its quality presets, and its "Same as stream" quality only gives the replay buffer one audio track.
  - Each recording is its own OBS process: `main` (primary quality, follows the mouse or focused app when auto switch is on, owns the audio tracks) plus `screen-<displayId>` per secondary screen (with auto switch, every screen gets one, and the Windows primary screen's uses primary quality; with auto switch and only one screen turned on, `main` follows across every screen, including the ones turned off, and there are no `screen-<displayId>` recorders, see `getFollowScreens`). `planRecorders` in `electron/utils/recordingPlan.js` decides the set; the renderer imports that same file to preview it. Each recorder runs from `userData/obs/recorders/<key>/` with junctions to the shared install, so it gets its own `config/` (portable OBS resolves `../../config` from its working folder). They're spawned hidden (`windowsHide` plus `SysTrayEnabled=false` in `user.ini`, so no window or tray icon; they still show as "OBS Studio" processes in Task Manager), driven over obs-websocket on random ports, and Node's job object kills them when ClipX exits.
  - Every hotkey save becomes a clip folder `ClipX Replays/<name>/` with the primary `<name>.mp4`, `Screen <n>.mp4` files and a `clip.json` manifest (`electron/utils/clipManifest.js`: files, roles, screens, audio track names, detected game). `<name>` comes from `getClipName`, e.g. `Clip 2026-Oct-25 [VALORANT] 03꞉52꞉30PM`: the detected game goes in the brackets (left out when there's none), and the time uses `꞉` (U+A789) because Windows doesn't allow `:` in file names. Recorders write to `ClipX Replays/.recording/` first (ignored by the index). The index stores `group_path`/`group_role` and hides `secondary` files from the grid; `local-clips:get-group` returns a clip's whole group for the future multi-screen viewer.
  - Clip notifications are ClipX's own overlay, not Windows toasts (Focus Assist hides those in games): `electron/services/toastService.js` shows `electron/toastWindow.html` as a transparent, click-through, non-focusable always-on-top window at a top corner of the screen being recorded, and the page synthesizes the chime with Web Audio. They fire only after a clip's files are in place, never on the hotkey press. Borderless and Windows' default fullscreen show them; true exclusive fullscreen doesn't, but the sound still plays.
  - The clip hotkey is polled with `GetAsyncKeyState` (`electron/utils/keyState.js`, every 25 ms) instead of Electron's `globalShortcut`: games that read raw input (e.g. League of Legends) switch off `RegisterHotKey` hotkeys while they're focused. Polling doesn't block the key from reaching other apps, and like OBS's own hotkeys it can't see keys while an app running as administrator is focused.
  - Track 1 is always the full mix (desktop audio plus the mic when a mic track exists), for normal playback. With any tracks added, the rest split the sound so a later mixer can raise, lower or mute each part by summing them instead of track 1: up to 4 sources (`planAudioTracks`), then a last track holding everything else. That's `Desktop audio` when only the mic is separated, otherwise `Other apps`: one hidden process capture per other app with a window, re-synced every 5 s. OBS has no "everything except these apps" capture, so sounds from apps without a window are only in track 1. Each capture follows one window per exe name, so when two separate programs share an exe (e.g. two Electron apps), only one of them reaches `Other apps`. OBS captures a process and all its children, so `pickOtherAudioApps` skips explorer.exe, any app with another windowed app under it (e.g. Steam running a game) and anything under a tracked app, otherwise the same sound would land on two tracks. `clip.json` lists each track's `kind`. The sliders on the Recording page apply while recording, and the app ones only change that app's own track, not track 1, so the split tracks only add up to track 1 when those sliders were at 100%. When mixing them with ffmpeg, `amix` divides by the number of inputs unless you pass `normalize=0`.
  - Editing clips from these folders (`ClipEditor.jsx`): saving a trim or uploading goes through `renderClipSegment` in `electron/services/clipService.js`, which always writes one audio track: track 1 copied while the user hasn't changed a volume, otherwise the user's mix (`buildAudioOutputOptions` in `electron/utils/audioMix.js`: `amix=normalize=0` plus `alimiter`, video still copied). The mixer only shows when every track has a `kind`. Its preview extracts each track with `-c copy` to `%TEMP%/clipx/tracks/` (deleted when the editor closes) and plays them through Web Audio gain nodes synced to the video, which is why the `clipx` scheme is `corsEnabled`; without that Web Audio gets silence. The `clipx` handler only serves requests whose referrer is the app's own loopback page, so remote frames (the Library's YouTube embeds) can't read local files through it. `renderStreamCopy` and the unused 4K render keep whatever audio their input has.
  - `clip.json` matches files by name, so `renameClip` updates the file's entry after renaming it. Saving a trim renames the original to `[ORIGINAL] <name>` and writes the trim to `ClipX Videos/` inside the clip's folder. `deleteClip` refuses a primary that still has screen files (they use its audio) and removes a deleted screen's entry; `deleteClipGroup` deletes every file and `clip.json`, then the folder only if it's empty. `getClipGroup` leaves out files that no longer exist. "Keep only <screen>" in the editor's Delete menu (`keepClipScreen`) deletes every other file; keeping a screen file first writes `<primary name> (Screen <n>).mp4` with that video and all of the primary's audio tracks (stream copy, aligned by end using lengths read from both files), which becomes the primary. Before anything is deleted, `clip.json` is rewritten with the kept file as primary and every other file as a secondary (so the group stays valid whichever deletes fail); afterwards the deleted files' entries are removed. Grouped files are indexed with the manifest's `createdAt` instead of the file's birthtime, so that new file keeps the clip's place in the grid.
  - Multi-screen clips: the grid shows one stacked card per primary with a screen count; the editor (`ScreenStage.jsx`, `src/lib/screenLayout.js`) shows one screen at a time with a button per screen under it, named after the Windows `primary` monitor ("Primary screen", "Secondary screen 1", …), and swipes toward the picked screen's side using each manifest `screen`'s desktop `x`/`y` (left to right by `number` when missing). It starts on the fixed primary or, with auto switch, the Windows `primary` monitor's file. Screen files have no audio, so the primary's audio plays (and is saved) alongside them. Files from separate OBS processes end within ~0.1 s of each other but can start several seconds apart (the replay buffer starts on a keyframe), so they're aligned by their end: a file's time plus `primary duration − its duration` is the primary's time. The editor keeps the playhead and trim points in the primary's time, so swapping screens doesn't move them. Saving a screen file maps its video with the primary's audio from that shifted time (`-itsoffset` when it falls before the primary starts). The replay buffer is `seconds + KEYFRAME_PADDING_SECONDS` (`obsConfig.js`), so files run a few seconds longer than the manifest's `seconds`. With auto switch, when `main` stayed on one screen for the whole buffer (`seconds + KEYFRAME_PADDING_SECONDS`, or since recording started), `getDuplicateScreen` drops one copy and the manifest stores the clip as a fixed primary on that screen. It compares `main`'s picture of that screen (letterboxed when the shapes differ) with the screen recorder's output height, fps and bitrate. If `main` is at least as good on all three and isn't letterboxed, the screen's recorder isn't saved. If the screen's file is at least as good on all three, `main`'s audio tracks are copied onto it (`moveAudioToScreen`, aligned by end) and that file becomes the primary. Otherwise both are kept. Clips without a `clip.json` (anything not recorded by ClipX) have a single audio track.
  - Game detection (`electron/services/gameDetectionService.js`) reads the foreground window through `koffi` (`electron/utils/foregroundWindow.js`), treats exes from `HKCU\System\GameConfigStore` and store install folders as games, and resolves IGDB ids via `/api/games?steam=<appid>` (Steam installs) or name search. Matches and user corrections are cached in `userData/games.json`; IGDB needs a signed-in user. Users can also assign a game to any app on the Recording page (for launchers with odd exe names, e.g. Plutonium); those are stored by exe name (`games.json` keys without a path) and count as the game while that process is running, even when it isn't in front. The detected game lasts until its process exits (the Recording page clears it then); a clip is tagged with the current game, or with one that closed within the clip's length.
- `api/` functions use `process.env.SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` (service role — never expose to the renderer) and authenticate callers with the user's Supabase access token as a Bearer token.

## CI & releases

- Pull requests to `master` run `ci.yml` on `windows-latest`. It runs `npm ci`, a `node --check` syntax pass over `api/`, `api-handlers/`, `electron/` and `scripts/`, then `npm test` and `build:react`. Last, it rebuilds the share player and fails if `public/clip-player/` differs from what's committed. GitHub skips `pull_request` runs when the PR's head commit message contains `[skip ci]`, so don't put it on PR commits.
- `master` push/tag `v*` triggers `release.yml`: builds, then creates a GitHub release from the `## vX.Y.Z` section in `CHANGELOG.md` (absent section ⇒ workflow fails). Bumper version in `package.json` must match a `## vX.Y.Z` heading.
- Pushing a version bump alone (no tag) releases as `v{version}`; the `dist/latest.yml` artifact powers in-app auto-updates.
- `release.yml` stops before building when a release for that tag already exists, so `master` pushes without a version bump leave every release alone. Before this check, those pushes rebuilt the current version's release files from whatever was on `master`. To rebuild a release's files from its own tag, run the **Rebuild release** workflow (`rebuild-release.yml`) with the tag: it replaces the installer, blockmap and `latest.yml` (keeping the release's original `releaseDate`; a tag whose build makes no `latest.yml`, like v1.0.2, has it removed) and leaves the notes and dates alone. Release runs for the same tag share a concurrency group (`release-<tag>`, set after a small job resolves the tag), so a run waits for the one before it and then sees the release that run created; runs for different tags don't wait on each other.
- A version with a pre-release part (e.g. `1.3.0-beta.1`) is published as a GitHub pre-release. Stable installs skip it unless `CLIPX_ALLOW_PRERELEASE=true` is set in the user's environment (read by the main process at launch). Installs already on a pre-release keep getting pre-releases. `/api/latest-version` ignores pre-releases, so opted-in installs find them on launch, on the hourly check or via Check for updates, not the 20s poll.
- To show a one-time how-to after an update, add a `# vX.Y.Z Title` section to `ANNOUNCEMENTS.md`; its body runs until the next `# vX.Y.Z` heading. It shows at the top of the post-update changelog popup for users updating from an older version to that version or later. Fresh installs don't see it.
- Only cut a release (version bump, `CHANGELOG.md` release section, `v*` tag) when the user explicitly asks for one.

## Code writing style

- All code should match the already established style in this repo, do not stray from a pattern that is already here.
- Do not make code too obscure and complicated, look for the simplest way to implement something while also satisfying common edge cases for the user.
- When adding a feature, ask yourself whether it should have tests, and if it should, add them in `tests/` (see `npm.cmd test` above for what those tests can import).
- When adding a modal, make sure clicking outside of it closes it and doesn't click any buttons behind the modal.
